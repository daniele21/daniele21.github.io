Performance Lab

A measurement layer for moving beyond “it runs”. Performance Lab is where Local AI systems are evaluated against the constraints that matter on real hardware.

01

DECIDE

A local model is only useful if the target workload survives the target hardware.

Performance Lab exists to turn 'can this run locally?' into a decision question rather than a demo milestone.

01

Can it run?

Establish whether a model and runtime fit the target device or local infrastructure at all.

02

Can it run well?

Measure the latency, throughput and resource trade-offs that determine whether the experience is practical.

03

Should it run locally?

Feed measured evidence back into the Local vs Hybrid vs Cloud decision.

02

BUILD

Define the measurement surface before collecting numbers.

The core dimensions stay explicit so a benchmark can answer a product question instead of producing isolated scores with no architectural consequence.

Latency

How long until a useful response arrives?

Throughput

How much work can the runtime sustain over time?

Memory

What footprint and pressure does the workload create?

Thermal / Battery

Does performance remain sustainable on the target device?

03

TEST

Run the workload on representative hardware, not just a convenient machine.

The experiment should preserve the actual model, runtime, configuration and device context needed to understand why a result is useful or misleading.

04

MEASURE

Publish measured evidence only when the run context is explicit.

This page currently defines the measurement layer and decision model. It does not publish a numeric benchmark dataset yet, so the previous decorative bar chart has been removed rather than implying results that are not present.

EVIDENCE BOUNDARY

The measurement framework is defined; representative benchmark results still need to be attached.

Performance Lab is intended to compare Local AI systems across latency, throughput, memory and device sustainability. Until real runs are published with model, runtime, configuration and hardware context, this page deliberately avoids numeric or chart-based performance claims.

Supported today

  • Decision questions are explicit: fit, practicality and deployment boundary
  • Latency, throughput, memory and thermal/battery are defined as core dimensions
  • Results are meant to feed back into Local vs Hybrid vs Cloud decisions

Not claimed here

  • Published representative benchmark runs
  • Model/runtime/device comparison table with reproducible configuration
05

DECIDE AGAIN

Use performance evidence to change the architecture when necessary.

The final output of the lab is not a leaderboard. It is a deployment decision that can confirm Local, move a workload to Hybrid, or keep it in Cloud when the measured constraints demand it.

CURRENT DECISION

Measurement is useful only when it can change the boundary.

Performance Lab exists to prevent 'local-first' from becoming ideology. A workload should stay local only when representative measurements show that quality, responsiveness and resource use remain acceptable for the actual product context.

  • Keep Local when the workload fits the target hardware
  • Use Hybrid when only part of the workflow is practical locally
  • Keep Cloud when measured constraints make local execution the wrong trade-off
