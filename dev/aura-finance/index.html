DECIDE

Can a budgeting product stay useful without making the cloud the owner of the ledger?

Aura starts from the user's decisions -safe-to-spend, spending patterns and unresolved transactions -while keeping the canonical financial workspace on the device first.

Why Aura exists

A personal budget should help you decide.

Aura starts from a simple constraint: understanding your finances should not require a cloud backend to become the owner of your complete financial history.

01

The goal is not more automation. It is more clarity without giving up ownership or control.

02

BUILD

Keep financial logic deterministic and platform-specific automation isolated.

The shared product owns the local ledger and finance rules; Android-specific payment detection stays behind a separate native capability, while optional cloud continuity is encrypted before data leaves the client.

The idea

One local financial workspace.
Clear signals, explicit control.

Aura keeps the canonical ledger on the device, derives its insights through deterministic finance rules, and treats imports or detected payments as proposals until you confirm them.

Under the hood

Local-first is an architecture boundary.

The shared React product and deterministic financial domain stay separate from Android-only capabilities, while cloud continuity remains optional and encrypted client-side.

React Native / Expo

Cross-platform core product, offline SQLite database, financial state engine and user experience.

Native Android Service

Background notification parsing, payment candidate detection and secure local IPC queue.

Client-Side Encryption

AES-256 encrypted payload serialization before optional Firebase cloud synchronization.

MEASURE

Be explicit about what the current product proves -and what it does not.

The current evidence is architectural and workflow-level rather than a comparative benchmark. The page therefore separates implemented ownership and review boundaries from claims that still need dedicated measurement.

EVIDENCE BOUNDARY

Current proof is about control, explainability and review boundaries.

Aura's documented implementation supports a local-first ledger, deterministic finance rules, review-before-recording Android payment candidates and optional client-side encrypted continuity. This page does not turn those properties into unsupported claims about detection accuracy or financial outcomes.

Supported today

  • Local workspace is the source of truth
  • Safe-to-spend and reporting derive from deterministic recorded data
  • Detected Android payments require explicit review before recording
  • Optional cloud payloads are encrypted client-side before synchronization

Not claimed here

  • Comparative payment-detection accuracy benchmark
  • Measured user-outcome improvement versus alternative budgeting tools
05

DECIDE AGAIN

Automate capture, not financial ownership.

The current product decision is to preserve a local source of truth and human-reviewed automation. Cloud continuity stays optional; detected events remain candidates until the user decides they belong in the ledger.

CURRENT DECISION

Keep the ledger local-first and automation reversible.

Aura uses automation to reduce repetitive capture without transferring authority over the financial history. The canonical transaction is created only after review, and optional cloud continuity remains a client-encrypted extension rather than the primary data owner.

  • Local device remains the canonical financial workspace
  • Automation proposes; the user confirms
  • Cloud continuity remains optional and client-encrypted
