01

DECIDE

Can sensitive-data detection adapt without moving the original document to cloud AI?

RedactGuard starts from a changing definition of PII: what is sensitive depends on the document, organization and workflow, while static detectors turn taxonomy changes into software maintenance.

The problem

Sensitive data is not a fixed list.

What must be protected changes by document, industry, organization and workflow. That makes detection both a privacy problem and a maintenance problem.

01

Manual review is slow

Long documents make anonymization repetitive, expensive and inconsistent.

02

Static rules are hard to adapt

New PII often means new regex, mappings, exceptions and application logic.

03

Cloud AI changes the privacy boundary

The original sensitive document must leave the machine before it can be analyzed.

The hidden cost: every change in what counts as sensitive can become a software change.
Why it matters

Privacy, adaptability and control.

01

Private by design

The document can be processed with local inference, without making cloud AI the default path for sensitive content.

02

Adaptable by configuration

New or changing PII can often be handled by updating the profile or prompt, instead of adding another detector.

Change the definition, not the software.
03

Human-controlled

AI accelerates detection, but the user decides what is actually removed before export.

02

BUILD

Make the sensitive-data definition configurable and keep inference local.

Profiles and custom PII instructions drive a local GGUF detector behind a separate document-processing boundary, so many taxonomy changes can update the definition rather than require another hard-coded detector.

The solution

Define what is sensitive.
RedactGuard finds it locally.

Standard identifiers or domain-specific information can be expressed through profiles and custom PII instructions used by the local LLM.

For many taxonomy changes, you update the definition instead of building another hard-coded detector.

Under the hood

Local by architecture.

Once the product idea is clear, the implementation is intentionally simple: UI, document processing, and local inference have separate responsibilities.

React / Vite

Upload, profile selection, human review and export workflow.

FastAPI + Docling

Document conversion, sessions, PII orchestration, redaction and caching.

Local GGUF LLM

Contextual PII detection through llama-cpp-python, including profile and custom-type instructions.

03

TEST

Keep every model finding visible and reversible before export.

The real product workflow is load → detect → review → redact → export. AI accelerates detection, but the user remains responsible for what is actually removed.

Product proof

Load. Review. Export.

The workflow stays visible and reversible until the user confirms the final redactions.

1 · LOAD

Choose the document and profile

Start from a built-in domain profile or a custom detection definition.

2 · REVIEW

Inspect every finding

Keep, remove or adjust what the local model identified as sensitive.

3 · EXPORT

Share the minimized result

Export only after the redaction choices have been explicitly reviewed.

04

MEASURE

Treat human review and model limitations as part of the evidence.

RedactGuard is an experimental privacy tool, not a compliance guarantee. The page therefore makes the implemented privacy boundary explicit while withholding unsupported claims about perfect PII recall or regulatory correctness.

EVIDENCE BOUNDARY

The workflow is implemented; detection remains fallible.

The current product supports local inference, configurable PII definitions, reviewable findings and minimized export. The underlying local model can still miss, misclassify or over-detect sensitive information, so human review remains mandatory.

Supported today

  • Document analysis can run through local GGUF inference
  • Standard and custom PII definitions are configurable
  • Every finding remains reviewable before export
  • The minimized result moves only after explicit user choices

Not claimed here

  • Compliance guarantee
  • Published perfect-recall or perfect-precision claim across PII domains
05

DECIDE AGAIN

Use local AI as an adaptable detector, not as an autonomous privacy authority.

The current product decision is to keep detection configurable and local while preserving a human confirmation step before any document is considered safe to share.

CURRENT DECISION

Change the definition, not the trust model.

RedactGuard uses a local LLM to make sensitive-data detection easier to adapt, but it does not transfer the final privacy decision to the model. The user reviews what was found and decides what is removed before export.

  • Local inference keeps the original document inside the chosen boundary
  • PII definitions can evolve through profiles and instructions
  • Human review remains required because model detection is fallible
Local-first data minimization

Define what is sensitive. Share less.

RedactGuard turns local AI into a configurable privacy workflow: define → detect → review → redact → export.
