WHAT THIS PROVES

Local AI becomes reusable Android infrastructure when applications depend on a stable consumer boundary instead of owning GGUF, JNI, model lifecycle and memory policy themselves.

Harnex already implements the shared runtime and Consumer SDK boundary; stronger production claims still depend on representative-device and lifecycle evidence.

WHY IT EXISTS

A local model inside one app is a feature. A shared runtime is infrastructure.

If every Android app owns model files, native bindings, lifecycle, memory policy and diagnostics, Local AI scales by duplication. Harnex moves those concerns behind one Android-owned host boundary.

One owner for expensive state

The host owns model bytes, native runtime state, residency and scheduling instead of duplicating them across products.

Small consumer boundary

Applications keep their workflow and integrate through a typed SDK/Binder contract rather than inheriting runtime internals.

Evidence before platform claims

Automated and emulator evidence proves contracts; physical Android evidence remains a separate release boundary.

THE INFRASTRUCTURE GAP

Without a host layer, every app rebuilds the hard parts.

The difficult work begins after the first successful generation: ownership, policy, lifecycle and failure semantics all need one authoritative place.

01

Duplicate the native stack

Each product otherwise carries GGUF handling, JNI, backend packaging and model lifecycle as application-specific infrastructure.

02

Couple product code to runtime policy

Model choice, presets, context, residency and authorization become scattered product decisions instead of explicit host policy.

03

Turn lifecycle failures into app bugs

Cancellation, Binder loss, process death, memory pressure and cleanup need durable semantics rather than ad-hoc recovery in every client.

ARCHITECTURE

One host boundary separates Android products from local inference infrastructure.

The execution path is Consumer app → Consumer Android SDK → signature-protected Binder → Harnex host/control plane → runtime orchestration → llama.cpp → curated GGUF. Model storage, observability and evaluation stay host-owned around that data plane.

RUNTIME & API

Consumer apps call a versioned SDK. Harnex keeps runtime ownership.

The supported direct dependency is the Consumer Android SDK. It owns public consumer contracts, Binder composition, typed transport failures, readiness inspection and durable logical jobs without exposing model-store or llama.cpp implementation types.

EVIDENCE & LIMITS

The shared runtime is implemented. Production readiness is not claimed.

The current development line proves the architecture, Consumer boundary and host behavior in code and automated integration. Representative Android hardware remains the boundary for stronger performance, memory, thermal and release claims.

EVIDENCE BOUNDARY

Implemented capability and release evidence are different things.

Harnex is an active engineering baseline. Automated and emulator evidence can prove contracts, failure semantics and cross-application integration, but it is not promoted into physical-device or production evidence.

Supported today

  • Consumer Android SDK and Binder shared-runtime boundary are integrated
  • Curated Qwen3.5 dense 0.8B / 2B model lifecycle and verified GGUF execution are implemented
  • Generation, streaming, cancellation, single-decode scheduling, memory-pressure handling and durable logical jobs are implemented
  • Host applications/use cases/presets/bindings plus Overview, Playground, Applications, Performance, Models, Diagnostics and Settings are integrated
  • Privacy-safe telemetry, health, performance and evaluation foundations are present

Not claimed here

  • Representative physical-device Qwen3.5 tuning plus memory and thermal evidence
  • Final physical two-APK shared-runtime and release gates
  • Remaining cross-process lifecycle convergence before stronger reliability claims

STATUS & NEXT DECISION

The next work is evidence hardening, not another architecture rewrite.

Keep the shared host/Consumer boundary stable and close the physical-device and lifecycle gates that determine whether it deserves stronger platform-level claims.

CURRENT DECISION

Treat Harnex as working infrastructure under validation, not as a production Android AI platform yet.

The shared runtime, SDK, control plane and local inference stack exist. The next confidence step comes from representative Android hardware and end-to-end process/lifecycle evidence rather than adding more abstraction.

  • Shared runtime + Consumer SDK already integrated
  • Physical memory, thermal and model-tuning evidence still required
  • Cross-process lifecycle and two-APK release evidence still being closed
